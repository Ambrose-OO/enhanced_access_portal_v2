# ADR-0004: Exclude generated migrations from the bandit scan and mark the remaining B104 finding as reviewed

Date: 2026-08-08
Status: Accepted

## Context
The security gate in the CI pipeline runs bandit, a static application
security testing tool, across the project at medium severity and above.
Its first run against the inherited IEAP codebase reported four B104
findings, described as a possible binding to all network interfaces.
Each finding is triggered by the string "0.0.0.0" appearing as the
default value of a CharField that stores a virtual machine's IP address.
No server is bound to that address anywhere in the project, so the rule
has matched on the literal string without the surrounding context.
Three of the four findings are located in files under
resource_dashboard/migrations/, which Django generates automatically,
not written or edited by hand. The remaining finding is in
resource_dashboard/models.py, which is authored code. Because a failing
gate blocks every merge, a decision was needed on how to resolve
findings that carry no genuine security risk.

## Options considered
1. Disable rule B104 across the whole project. This clears the failure
   in one change, but it also removes detection of any future code that
   genuinely binds a service to all interfaces, which is the risk the
   rule exists to catch.
2. Exclude the generated migrations directory from the scan and mark
   the single authored occurrence with a nosec comment stating the
   reason. The rule remains active everywhere else, and each suppression
   is visible in the code and counted in bandit's output.
3. Change the field default so that the string no longer appears, for
   example by using an empty value or allowing null. This removes the
   finding at source, but it alters the data model and its migrations,
   which is a change to application behaviour rather than to the
   pipeline, and is therefore not appropriate while establishing the
   gate.

## Decision
Option 2 has been chosen. The bandit step in the workflow now excludes
paths matching */migrations/*, and the occurrence in
resource_dashboard/models.py carries a nosec comment recording that the
value is a database default rather than a network bind (PyCQA, no date).
Option 3 is retained as a candidate improvement and is recorded on the
backlog for a later time box.

## Consequences
Positive:
1. The security gate returns to a passing state without weakening the
   rule set, so B104 continues to apply to all authored code.
2. The scan is focused on code written by the developer, since generated
   migration files are not a meaningful target for static application
   security testing.
3. Each suppression states its justification at the point of use, and
   bandit reports the number of nosec markers on every run, so the
   decision remains visible rather than hidden.
4. The judgement applied here demonstrates that automated gates report
   findings for human assessment rather than replacing it, which is a
   recognised limitation of static analysis tooling.

Negative:
1. Any future security defect introduced within a migration file will not
   be detected, although the risk is low because these files are
   generated rather than hand written.
2. A nosec marker suppresses the finding permanently unless it is
   reviewed, so the marker and its stated reason must be revisited if
   the field is ever repurposed.
3. The underlying oddity of using an address literal as a placeholder
   default remains in the data model until the improvement recorded on
   the backlog is carried out.
