# ADR-0006: Single stage Render web service deployment with ephemeral SQLite storage

Date: 2026-08-20

Status: Accepted

## Context
The application needed a publicly reachable hosted environment in order to
demonstrate the delivery and deployment stages of the lifecycle. The project is
a Django monolith using SQLite, developed by a single apprentice under a fixed
submission deadline, and the hosting budget is limited to free tier services.
Render's free tier provides no persistent disk, so any file written by a running
instance, including the SQLite database, is discarded when the instance is
rebuilt or restarted. Django also declines to serve static files when the debug
flag is off, which conventionally requires a separate web server in front of the
application.

## Options considered
1. A single web service using the committed SQLite database, accepting that
   data written through the deployed site does not persist. The repository
   contains sample records and logins, so each deploy returns the site to a
   known demonstration state.
2. A web service together with Render's free PostgreSQL instance. This provides
   genuine persistence, but adds a database dependency, configuration changes
   and a migration step to an iteration that is already constrained by time.
3. Separate staging and production services, as described in the coding plan.
   This allows validation against a deployed environment before release, but
   doubles the setup effort and the cold start waiting on the free tier.

## Decision
Option 1 has been chosen for this iteration. A single Render web service is
deployed from the l6_dev_ops_main branch, running gunicorn as the production
server and using whitenoise to serve static files from the application itself,
which avoids the need for a separate web server (Render, no date). The
production secret, debug flag and allowed hosts are supplied as environment
variables rather than committed, following ADR-0005. A staging service and a
managed database remain recorded on the backlog.

## Consequences
Positive:
1. The application is publicly reachable, so the delivery and deployment stages
   of the lifecycle can be evidenced rather than described.
2. The deployment is reproducible from pinned manifests, since the host installs
   from requirements.txt and uses the interpreter named in the PYTHON_VERSION
   variable, matching the versions used locally and in CI.
3. Static files are collected and compressed during the build, so no additional
   infrastructure is required to serve them.
4. Each deploy restores a known demonstration state, which is convenient for
   assessment because the sample logins are always present.

Negative:
1. Data created through the deployed site does not persist across deploys or
   restarts. This is acceptable for an assessed prototype but would not be
   acceptable for a production system, where option 2 would be adopted.
2. The free instance sleeps after a period of inactivity, so the first request
   after a pause takes appreciably longer to respond. This is documented in the
   README so that the delay is not mistaken for a fault.
3. Without a staging service, validation occurs against production rather than
   before it, which places greater weight on the CI gates and the post-deploy
   smoke test.
