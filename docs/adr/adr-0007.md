# ADR-0007: Deployment triggers from the pipeline rather than from repository pushes

Date: 2026-08-21

Status: Accepted

## Context
Render deploys automatically when a commit is pushed to the connected branch.
This behaviour is independent of the CI pipeline, so a commit would reach the
running service whether or not the build, static analysis, security and test
gates had passed. The coding plan for this project specifies continuous
delivery rather than just continuous deployment solely, meaning that release is 
guarded rather than automatic, and the branch protection rule already established 
in Iteration 0 exists to ensure that nothing untested reaches the deployment
branch.

## Options considered
1. Retain automatic deployment on push. This is the simplest configuration,
   but it means the pipeline reports on quality without controlling release,
   so a red pipeline and a live deployment could coexist.
2. Disable automatic deployment and call a Render deploy hook from a workflow
   job that depends on the gate job. Deployment then occurs only when every gate
   has passed, and only on the deployment branch.
3. Require a manual deployment from the Render dashboard after each merge. This
   is fully controlled but is a manual step in an otherwise automated pipeline,
   and it is easily forgotten.

## Decision
Option 2 has been chosen. Automatic deployment is disabled on the service, and
the deploy hook URL is stored as an encrypted repository secret. A deploy job in
the workflow depends on the gate job and is restricted by condition to the
l6_dev_ops_main branch, so pull request runs verify without deploying. A
post-deploy smoke test then requests a known page on the live site and fails the
run if the response is not successful.

## Consequences
Positive:
1. Deployment is conditional on the pipeline, so the continuous delivery claim
   made in the report is enforced mechanically rather than asserted.
2. The deploy hook URL is held as a repository secret rather than in the
   workflow file, so it is not exposed in the public repository.
3. The smoke test verifies the deployed application rather than the build,
   which is the only check in the pipeline that exercises production settings on
   the real host.
4. Pull request runs are unaffected, because the branch condition prevents the
   deploy job from running outside the deployment branch.

Negative:
1. The smoke test waits a fixed period before running, which is a crude
   approximation of deploy completion. A short build may waste time and a slow
   build or cold start could cause a false failure. Polling the Render API is
   recorded on the backlog as the more robust alternative.
2. Deployment now depends on the workflow succeeding, so a fault in the pipeline
   configuration prevents release even when the application is sound, as
   occurred during this iteration.
3. A failed smoke test reports the problem but does not roll back, so recovery
   remains a manual action guided by the runbook.
