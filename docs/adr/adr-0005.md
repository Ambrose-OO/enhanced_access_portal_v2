# ADR-0005: Django SECRET_KEY to be read from an environment variable

Date: 2026-08-13
Status: Accepted

## Context
The security gate in the CI pipeline runs bandit across the project. Once
low severity reporting was enabled, it reported a B105 finding against
enhanced_access_portal/settings.py, where the Django SECRET_KEY was
assigned as a string literal in the source file. Django uses this value
to sign session cookies, password reset tokens and cross site request
forgery tokens, so knowledge of it would allow an attacker to forge a
session and authenticate as any user, including an administrator. The
repository is public, so the value was readable by anyone, and it is
present in the history of every prior commit. This is a genuine defect
rather than a false positive, and it corresponds to the security
misconfiguration category of the OWASP Top 10.

## Options considered
1. Leave the value in place and suppress the finding. This clears the
   gate but leaves a working credential published in a public
   repository, so it does not address the defect at all.
2. Read the value from an environment variable at runtime, with a
   clearly labelled insecure fallback for local development, and rotate
   the exposed value. The secret is then supplied by the hosting
   environment and never enters version control.
3. Store the value in a separate configuration file that is excluded
   from version control. This also keeps the secret out of the
   repository, but it introduces a file that must be created manually on
   every machine, and it is easily committed by accident.

## Decision
Option 2 has been chosen. The assignment in settings.py now reads
SECRET_KEY from the DJANGO_SECRET_KEY environment variable, falling back
to a string that is explicitly named as insecure and intended for local
development only. A replacement key has been generated and will be
configured as an environment variable on the Render service, so the
production value exists only in the hosting platform and is never
committed. The previously published value is treated as compromised and
is no longer in use.

## How the lookup works
The mechanism is provided by the Python standard library rather than by
Django, so it is recorded here for clarity.

1. os.environ is a mapping object representing the environment variables
   of the running process. It behaves like a dictionary, in which the
   keys are variable names and the values are their contents.
2. Because it is a mapping, it supports the standard get method, whose
   documented behaviour is to return the value for the given key if that
   key is present, and otherwise to return the supplied default as 
   a string literal. Where no default is supplied, it returns None 
   (Python Software Foundation, no date).
3. The first argument is therefore a key, meaning the name of the
   environment variable to look up. It is not itself a secret and holds
   no value. DJANGO_SECRET_KEY is simply the label chosen for the
   variable that will carry the real secret in production, comparable to
   the name written on a pigeonhole rather than its contents.
4. The second argument is the default, an ordinary value returned when
   that name is not present in the environment. Here it is a string
   literal, and it becomes the actual secret key whenever the lookup
   fails.
5. In practice this means the fallback is used on the developer machine
   and on the CI runner, where no such variable exists, while the
   rotated key is returned on Render, where the variable is configured.
   The get method is used in preference to square bracket access because
   the latter raises a KeyError when the variable is absent, which would
   prevent the application from starting.

## Consequences
Positive:
1. No secret is stored in the repository, so the value cannot be read
   from the public codebase or leaked through a future commit.
2. The production secret is held by the hosting platform and can be
   rotated there without any change to the source code.
3. Local development and continuous integration run on the fallback
   value without requiring configuration, so the change adds no setup
   burden.
4. The defect was found by an automated gate in code that had been
   running for some time, which demonstrates the value of including
   static application security testing in the pipeline.

Negative:
1. The original value remains recoverable from the commit history.
   Rewriting the history was judged disproportionate and risky at this
   stage of the project, so the exposure has instead been neutralised by
   rotating the key, meaning the published value no longer grants access
   to anything.
2. The application will run on the insecure fallback if the environment
   variable is ever absent in a deployed environment, so the variable
   must be verified as part of the deployment configuration.
3. Two further settings in the same file, the debug flag and the allowed
   hosts list, carry values that are unsuitable for production. These
   are recorded on the backlog for a settings hardening time box rather
   than being addressed here.
